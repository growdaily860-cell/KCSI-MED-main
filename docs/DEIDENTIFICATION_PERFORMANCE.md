# 비식별화 성능 수치 만들기

"스캔서류 N건 중 X% 판독 가능" 같은 문장을 **근거를 대고** 말할 수 있게 하는 구조다.
두 갈래로 나뉜다.

| 갈래 | 무엇을 재나 | 분모 | 정답지 |
|---|---|---|---|
| **처리기록** (1단계) | 실사용에서 자동 탐지가 얼마나 동작했나 | 실제로 처리한 문서 | 없음 |
| **합성 문서 채점** (2단계) | 개인정보를 빠짐없이 가렸나 | 합성 문서 세트 | 있음 |

두 수치는 다른 것을 재므로 **바꿔 쓰면 안 된다.** 처리기록은 "얼마나 손이 덜 갔나"이고,
합성 문서 채점은 "얼마나 안전한가"다.

## "판독 가능"의 정의

이 저장소는 **판독 성공 = 그 문서의 개인정보 항목을 하나도 빠뜨리지 않고 가림** 으로 정의한다.

OCR이 글자를 읽었는지로 정의하지 않는다. 글자를 다 읽고도 주민등록번호 하나를 놓치면
비식별화는 실패한 것이고, 그걸 성공으로 세는 지표는 위험하다.

## 1단계 · 처리기록

`/field`에서 의료기록을 비식별화할 때마다 결과가 브라우저에 쌓인다
(`kcsi_deident_doc_log_v1`, 최근 500건).

**남기는 것**: 문서별 결과 분류, OCR 성공 여부·평균 신뢰도·단어 수, 자동/수동 가림 상자 수,
항목 종류별 개수, 소요 시간, 해상도, 촬영 조건 라벨
**남기지 않는 것**: 문서 이미지, 인식된 글자, 개인정보 값, **파일명**(환자 이름이 들어가는 일이 잦다)

결과 분류는 네 가지다.

| 분류 | 뜻 |
|---|---|
| `auto` | 자동 탐지만으로 끝났다 |
| `manual_assisted` | 자동이 찾았지만 사람이 더 그리거나 지웠다 |
| `manual_only` | 자동 탐지가 실패해 사람이 전부 그렸다 |
| `failed` | 가림 상자 없이 끝났다 — **비식별화되지 않은 상태** |

### 수치 꺼내기

브라우저 개발자도구 콘솔에서:

```js
KCSI_DEID.docLogSentences().join('\n')   // 바로 인용할 수 있는 문장
KCSI_DEID.summarizeDocLog()              // 숫자만
copy(KCSI_DEID.docLogCsv())              // CSV를 클립보드로
KCSI_DEID.clearDocLog()                  // 기록 비우기
```

문장은 표본 수와 조건을 **반드시 포함하도록** 코드가 만든다. 비율만 손으로 옮겨 적다 보면
근거가 빠지기 때문이다.

## 2단계 · 합성 문서 채점

실제 의료기록은 개인정보라 저장소에 넣을 수 없다. 대신 가짜 값으로 채운 문서를 만든다.
값을 우리가 그렸으므로 **어디에 어떤 개인정보가 있는지 정확히 안다**.

```bash
npm install --no-save sharp
npm run build:docs                                  # 서식 3종 × 조건 8종 × 5건 = 120건
node scripts/build-doc-samples.mjs --per=2          # 조건별 2건
node scripts/build-doc-samples.mjs --forms=diagnosis,lab
```

`samples/KCSI_MED_synthetic_docs.zip` 과 매니페스트가 나온다. 인터넷은 필요 없다.

### 서식과 조건

* 서식 3종: 진단서 · 처방전 · 검사결과 통보서
* 조건 8종: 정상 / 접힘 / 구겨짐 / 기울어짐 5° / 기울어짐 15° / 저조도 / 스캔 노이즈 / 저해상도
* 항목 6종: 성명 · 주민등록번호 · 생년월일 · 전화번호 · 주소 · 개인식별번호

**접힘·구겨짐은 음영으로 흉내 낸 것이고 기하 왜곡은 기울어짐 조건에만 있다.** 좌표를 정확히
옮길 수 없는 변형은 넣지 않았다 — 정답지가 틀리면 그 표본으로 낸 모든 수치가 틀린다.

모든 값은 지어낸 것이며, 주민등록번호는 존재할 수 없는 조합(13월·32일 이상)을 쓴다.

### 채점

`scoring/doc-redaction.js`가 가림 상자와 정답 항목을 맞춰 본다.

| 지표 | 산출 | 의미 |
|---|---|---|
| `complete` | 항목을 하나도 빠뜨리지 않았는가 | 문서 단위 "판독 성공" |
| `recall` | 가려진 항목 ÷ 전체 항목 | 안전 기준 |
| `overRedactionFactor` | 칠한 넓이 ÷ 항목 넓이 | 과잉 가림. **문서를 통째로 칠하면 재현율은 100%가 되므로 이 값을 함께 봐야 한다** |
| `strayBoxes` | 어떤 항목과도 겹치지 않은 상자 수 | 엉뚱한 곳을 가린 횟수 |

항목 넓이의 90% 이상이 덮여야 가려진 것으로 센다. 여러 상자로 나눠 덮어도 인정한다.

## 인용할 때의 규칙

1. **표본 수 없이 비율만 쓰지 않는다.** "100% 판독 가능"은 그 자체로 근거가 없는 문장이다.
2. **조건을 밝힌다.** 정상 스캔과 열화 조건은 따로 적는다.
3. **합성 문서 기준임을 밝힌다.** 실제 스캔본은 종이질·스캐너·조명이 제각각이라 다르다.
4. **재현율과 과잉 가림을 함께 적는다.** 하나만 적으면 반쪽이다.

### 문장 예시

> 합성 의료문서 **120건**(서식 3종 × 촬영조건 8종) 기준, 정상 스캔 **15건 중 15건(100%)** 에서
> 개인정보 항목을 빠짐없이 가렸습니다. 접힘·구겨짐·기울어짐 등 열화 조건 **105건** 에서는
> **N건(X%)** 이었고, 누락이 발생한 문서는 모두 사용자 수동 가림으로 보완할 수 있었습니다.
> 과잉 가림은 항목 넓이의 평균 **N배** 수준이었습니다.
> *(합성 문서 기준이며 실제 스캔 문서 성능과 다를 수 있습니다.)*

## 아직 없는 것

* 화면에서 수치를 보는 패널이 없다. 지금은 콘솔 API로 꺼내야 한다.
* 합성 문서를 자동으로 돌려 채점하는 배치 실행기가 없다. 문서를 `/field`에 넣어
  처리한 뒤 가림 상자를 정답지와 맞춰 보는 과정은 아직 수동이다.
