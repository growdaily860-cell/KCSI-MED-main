# 비식별화 성능 수치 만들기

"스캔서류 N건 중 X% 판독 가능" 같은 문장을 **근거를 대고** 말할 수 있게 하는 구조다.
두 갈래로 나뉜다.

| 갈래 | 무엇을 재나 | 분모 | 정답지 |
|---|---|---|---|
| **처리기록** (1단계) | 실사용에서 자동 탐지가 얼마나 동작했나 | 실제로 처리한 문서 | 없음 |
| **합성 문서 채점** (2단계) | 개인정보를 빠짐없이 가렸나 | 합성 문서 세트 | 있음 |

두 수치는 다른 것을 재므로 **바꿔 쓰면 안 된다.** 처리기록은 "얼마나 손이 덜 갔나"이고,
합성 문서 채점은 "얼마나 안전한가"다.

## "판독 가능"의 정의

이 저장소는 **항목 재현율 = 정답지의 개인정보 항목 중 넓이의 90% 이상이 가려진 비율** 을
주 지표로 쓴다.

OCR이 글자를 읽었는지로 정의하지 않는다. 글자를 다 읽고도 주민등록번호 하나를 놓치면
비식별화는 실패한 것이고, 그걸 성공으로 세는 지표는 위험하다.

### "완전 비식별화"를 주 지표에서 내린 이유

예전에는 **문서 단위**로 "항목을 하나도 안 빠뜨렸는가"(`complete`)를 앞세우고 그걸
**완전 비식별화**라 불렀다. 두 가지가 잘못됐다.

* **이름이 사실보다 크다.** "완전 비식별화"는 통과한 문서가 법적으로 안전하다는 뜻으로
  읽힌다. 실제로 재는 것은 "우리가 만든 정답지에 적힌 항목을 다 가렸는가"뿐이고,
  정답지에 없는 개인정보는 애초에 세지 않는다. 이름을 **누락 0건 문서**로 바꿨다.
* **너무 무디다.** 항목 7개 중 6개를 가린 문서와 하나도 못 가린 문서가 똑같은 실패로
  묶인다. 규칙을 고쳐 누락을 절반으로 줄여도 이 숫자는 그대로일 수 있어, 무엇이
  나아졌는지 알려주지 못한다.

그래서 지표를 이렇게 나눴다.

| 지표 | 자리 | 무엇을 답하나 |
|---|---|---|
| **항목 재현율** | 주 지표 | 전체 개인정보 항목 중 몇 %를 가렸나 |
| **고위험 항목 재현율** | 주 지표 | 주민등록번호·개인식별번호를 몇 % 가렸나 |
| **문서당 평균 누락 항목 수** | 보조 | 문서 한 건에 평균 몇 개가 남나 |
| **누락 항목 수 분포** (0 / 1 / 2개 이상) | 보조 | 위험이 몇몇 문서에 몰렸나, 고루 퍼졌나 |
| 누락 0건 문서 | 참고 | 예전 `complete`. 이름만 바꿔 남겨 뒀다 |

고위험 항목을 따로 뽑는 이유는, 전체 평균 하나로는 주민등록번호가 통째로 빠져도
다른 항목에 묻혀 보이지 않기 때문이다.

## 규칙 상한선 — 누락의 원인을 가른다

항목이 누락됐을 때 원인은 둘 중 하나다.

1. **OCR이 글자를 못 읽었다** — 촬영·해상도 문제
2. **읽었어도 규칙이 그 칸을 개인정보로 보지 않는다** — 규칙 문제

실측치 하나만 보면 둘이 섞인다. 스캔 품질을 아무리 올려도 넘을 수 없는 벽을 품질 탓으로
오해하게 되고, 반대로 규칙 공백을 촬영 문제로 덮어 두게 된다.

`scoring/rule-ceiling.js`는 정답지의 **라벨과 값을 이미지 대신 글자로 규칙에 직접 넣어**
"OCR이 완벽했다면 몇 %를 잡았을까"를 계산한다. `/deid-report`가 이 값을 실측치와 나란히
표시한다.

```
규칙 상한 100% / 실측 61.2%
  규칙 공백  0.0%p   ← 100% − 상한. 규칙을 고쳐야 줄어든다
  OCR 손실  38.8%p   ← 상한 − 실측. 촬영·해상도로 줄어든다
```

규칙이 못 잡는 칸은 **라벨 이름과 함께** 나온다("보호자 3건"). "몇 % 부족하다"보다
고칠 곳을 바로 짚어 준다.

실측한 이력:

| 시점 | 규칙 상한 | 막고 있던 것 |
|---|---|---|
| 도입 시 | 88.2% (600/680) | 담당의사·처방의사 이름을 어느 규칙도 잡지 않았다. 진단서 6/7, 처방전 4/5 |
| 의료인 성명 규칙 추가 후 | **100%** (680/680) | 없음 |

상한이 88.2%였을 때 "누락 0건 문서"의 상한은 **33.3%**였다 — 서식 3종 중 2종은 OCR이
완벽해도 구조적으로 통과가 불가능했다. 주 지표를 문서 단위에 두면 안 되는 이유가 이것이다.

정답지에 라벨·값이 없는 옛 팩에서는 상한선을 **계산하지 않고 그렇다고 알린다**. 0%로
뭉개면 규칙이 망가진 것처럼 보인다.

## 1단계 · 처리기록

`/field`에서 의료기록을 비식별화할 때마다 결과가 브라우저에 쌓인다
(`kcsi_deident_doc_log_v1`, 최근 500건).

**남기는 것**: 문서별 결과 분류, OCR 성공 여부·평균 신뢰도·단어 수, 자동/수동 가림 상자 수,
항목 종류별 개수, 소요 시간, 해상도, 촬영 조건 라벨
**남기지 않는 것**: 문서 이미지, 인식된 글자, 개인정보 값, **파일명**(환자 이름이 들어가는 일이 잦다)

결과 분류는 네 가지다.

| 분류 | 뜻 |
|---|---|
| `auto` | 자동 탐지만으로 끝났다 |
| `manual_assisted` | 자동이 찾았지만 사람이 더 그리거나 지웠다 |
| `manual_only` | 자동 탐지가 실패해 사람이 전부 그렸다 |
| `failed` | 가림 상자 없이 끝났다 — **비식별화되지 않은 상태** |

### 수치 보기 — `/deid-report`

배포된 사이트의 **`/deid-report`** 로 들어가면 두 갈래 수치를 한 화면에서 본다.

1. **실사용 처리기록** — 요약 타일, 인용할 수 있는 문장, 조건별 표, CSV 내려받기
2. **합성 문서 배치 측정** — ZIP을 불러와 자동 탐지에 태우고 조건별·항목별 재현율을 낸다
3. **인용 규칙** — 표본 수·조건·합성 여부·과잉 가림을 빼먹지 않도록 화면에 붙여 뒀다

문장은 **문장 복사** 버튼으로 그대로 가져갈 수 있다.

### 콘솔에서 꺼내기

화면 없이 값만 필요하면 개발자도구 콘솔에서:

```js
KCSI_DEID.docLogSentences().join('\n')   // 바로 인용할 수 있는 문장
KCSI_DEID.summarizeDocLog()              // 숫자만
copy(KCSI_DEID.docLogCsv())              // CSV를 클립보드로
KCSI_DEID.clearDocLog()                  // 기록 비우기
```

문장은 표본 수와 조건을 **반드시 포함하도록** 코드가 만든다. 비율만 손으로 옮겨 적다 보면
근거가 빠지기 때문이다.

## 2단계 · 합성 문서 채점

실제 의료기록은 개인정보라 저장소에 넣을 수 없다. 대신 가짜 값으로 채운 문서를 만든다.
값을 우리가 그렸으므로 **어디에 어떤 개인정보가 있는지 정확히 안다**.

```bash
npm install --no-save sharp
npm run build:docs                                  # 서식 3종 × 조건 8종 × 5건 = 120건
node scripts/build-doc-samples.mjs --per=2          # 조건별 2건
node scripts/build-doc-samples.mjs --forms=diagnosis,lab
```

`samples/KCSI_MED_synthetic_docs.zip` 과 매니페스트가 나온다. 인터넷은 필요 없다.

정답지(`answer_sheet.json`)의 항목은 종류·좌표와 함께 **라벨과 값**을 담는다(스키마 v2).
규칙 상한선을 계산하려면 값이 필요하기 때문이다. 값은 전부 합성값이라 저장해도 개인정보가
아니다. 이미 커밋된 팩은 `node scripts/backfill-doc-answers.mjs` 로 이미지를 다시 만들지 않고
정답지만 채울 수 있다 — 새로 계산한 좌표가 기존 좌표와 한 픽셀이라도 다르면 아무것도 쓰지
않고 멈춘다.

### 서식과 조건

* 서식 3종: 진단서 · 처방전 · 검사결과 통보서
* 조건 8종: 정상 / 접힘 / 구겨짐 / 기울어짐 5° / 기울어짐 15° / 저조도 / 스캔 노이즈 / 저해상도
* 항목 6종: 성명 · 주민등록번호 · 생년월일 · 전화번호 · 주소 · 개인식별번호
* 성명에는 **환자 이름과 의료인 이름(담당의사·처방의사)이 모두** 들어간다

**접힘·구겨짐은 음영으로 흉내 낸 것이고 기하 왜곡은 기울어짐 조건에만 있다.** 좌표를 정확히
옮길 수 없는 변형은 넣지 않았다 — 정답지가 틀리면 그 표본으로 낸 모든 수치가 틀린다.

모든 값은 지어낸 것이며, 주민등록번호는 존재할 수 없는 조합(13월·32일 이상)을 쓴다.

### 배치 측정 실행

`/deid-report` → **ZIP 불러와 측정** 을 누르면 `samples/KCSI_MED_synthetic_docs.zip` 을 받아
문서를 하나씩 자동 탐지에 태운다. 다른 ZIP을 쓰려면 **다른 ZIP 선택**을 누른다.

측정 경로는 사람 확인 창을 띄우지 않고 **비식별화 사본도 만들지 않는다**(`KCSI_DEID.detectOnly`).
실제 비식별화는 `/field`의 확인 흐름에서만 일어난다.

문서 한 건이 실패해도 배치는 멈추지 않고, 실패한 문서는 **분모에서 빠지지 않는다** —
실패를 빼고 계산하면 성능이 실제보다 좋아 보인다.

빠른 확인은 8건, 조건별 경향은 24건, 발표용 수치는 전체를 돌린다. 브라우저에서 OCR을 돌리므로
문서 한 건당 수 초가 걸린다.

### 채점

`scoring/doc-redaction.js`가 가림 상자와 정답 항목을 맞춰 본다.

| 지표 | 산출 | 의미 |
|---|---|---|
| `itemRecall` | 가려진 항목 ÷ 전체 항목 | **주 지표.** 안전 기준 |
| `highRiskRecall` | 주민등록번호·개인식별번호만 따로 | 유출 피해가 가장 큰 항목 |
| `meanMissedPerDoc` | 남은 항목 수 ÷ 문서 수 | 문서 한 건당 남은 위험의 크기 |
| `missDistribution` | 누락 0 / 1 / 2개 이상 문서 수 | 위험이 몰렸나 퍼졌나 |
| `complete` | 항목을 하나도 빠뜨리지 않았는가 | 참고. 화면에는 **누락 0건 문서**로 적는다 |
| `recall` | 문서 하나의 가려진 항목 비율 | 문서 단위 재현율 |
| `overRedactionFactor` | 칠한 넓이 ÷ 항목 넓이 | 과잉 가림. **문서를 통째로 칠하면 재현율은 100%가 되므로 이 값을 함께 봐야 한다** |
| `strayBoxes` | 어떤 항목과도 겹치지 않은 상자 수 | 엉뚱한 곳을 가린 횟수 |

항목 넓이의 90% 이상이 덮여야 가려진 것으로 센다. 여러 상자로 나눠 덮어도 인정한다.

## 인용할 때의 규칙

1. **표본 수 없이 비율만 쓰지 않는다.** "100% 판독 가능"은 그 자체로 근거가 없는 문장이다.
2. **조건을 밝힌다.** 정상 스캔과 열화 조건은 따로 적는다.
3. **합성 문서 기준임을 밝힌다.** 실제 스캔본은 종이질·스캐너·조명이 제각각이라 다르다.
4. **재현율과 과잉 가림을 함께 적는다.** 하나만 적으면 반쪽이다.
5. **"완전 비식별화"라고 부르지 않는다.** 법적 안전으로 읽힌다. **누락 0건 문서**라고 적는다.
6. **규칙 상한과 실측을 함께 적는다.** 남은 격차가 규칙 공백인지 OCR 손실인지 밝힌다.

### 문장 예시

> 합성 의료문서 **120건**(서식 3종 × 촬영조건 8종, 개인정보 항목 **680개**) 기준,
> 항목 **N개(X%)** 를 자동으로 가렸습니다. 유출 피해가 큰 주민등록번호·개인식별번호는
> **240개 중 N개(X%)** 였습니다. 같은 정답지를 이미지 대신 글자로 규칙에 직접 넣으면
> **100%** 가 잡히므로, 남은 격차는 규칙 공백이 아니라 OCR이 글자를 읽지 못해 생긴
> 손실입니다. 정상 스캔 **15건**과 열화 조건 **105건**을 나눠 보면 각각 **X% / Y%** 였고,
> 남은 항목은 사용자 수동 가림으로 비식별화할 수 있습니다. 과잉 가림은 항목 넓이의
> 평균 **N배** 수준이었습니다.
> *(합성 문서 기준이며 실제 스캔 문서 성능과 다를 수 있습니다.)*

## 한계

* 합성 문서는 실제 스캔본이 아니다. 종이질·스캐너·조명·글꼴이 실제와 다르므로 여기서 낸
  수치는 **기능 검증과 조건 간 비교**에 쓰고, 절대적인 성능 주장으로 쓰지 않는다.
* 접힘·구겨짐은 음영으로 흉내 낸 것이라 실제 종이 왜곡보다 쉽다.
* 실사용 처리기록에는 정답지가 없다. "몇 %가 자동으로 처리됐다"는 말할 수 있어도
  "몇 %를 빠짐없이 가렸다"는 말할 수 없다. 후자는 합성 문서 채점에서만 나온다.
* 측정은 브라우저에서 돈다. 기기 성능에 따라 소요 시간이 크게 달라진다.
* **규칙 상한 100%는 이 합성 서식에 대해서만 참이다.** 상한은 "정답지에 적힌 라벨·값을
  현재 규칙이 잡는가"를 재므로, 우리가 쓰지 않은 서식·라벨(예: 보호자, 군번, 외국인등록번호)은
  애초에 분모에 없다. 상한이 100%라는 말은 "규칙에 공백이 없다"가 아니라
  **"이 표본이 규칙 공백을 더 이상 못 찾는다"** 는 뜻이다. 새 서식을 추가하면 다시 내려간다.
