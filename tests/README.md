# KCSI Copilot med — 회귀 테스트

`index.html`(단일 파일 PWA)을 브라우저 없이 Node에서 검사한다.
`<script>` 블록만 뽑아 스텁 환경에서 실행하는 방식.

## 실행

```bash
npm install
npm test
```

종료코드 `0`=PASS, `1`=FAIL. 둘 다 통과해야 배포.

## 무엇을 보는가

### tdz.js
최상위 `const`/`let`을 **즉시 실행되는 코드**에서 선언 전에 참조하는지.
3,800줄이 단일 스코프라 TDZ 하나면 스크립트 전체가 죽고 **화면이 백지**가 된다.

- 즉시 실행 = 최상위 문장 + IIFE 본문
- 지연 실행(콜백·이벤트핸들러·함수 본문)은 로드 완료 후에 돌므로 제외
- 예: `checkForUpdate` IIFE의 `untouched()`가 `img`(아래에서 `let` 선언)를 참조하지만
  `.then()` 콜백 안이라 안전 — 이 테스트가 정확히 구분해야 하는 경계

### dom.js
스텁 DOM에서 스크립트가 **끝까지 실행되는지**(로드 단계 사망 감지).

핵심 설계: `getElementById`는 **실제 마크업에 있는 id만** 엘리먼트를 돌려주고
나머지는 `null`을 반환한다. 아무거나 돌려주는 스텁이면 없는 엘리먼트를 만지는
코드를 못 잡는다.

로드 완주 판정은 주요 전역 10개(`visionAnalyze`, `verifyPills`, `refreshFwdBtn`,
`runForensicHints`, `renderPillCard`, `searchGrn`, `lookupPill`, `buildReportText`,
`appendCard`, `clearResultSegs`)의 정의 여부로 한다.

> `vm` 컨텍스트에서 최상위 `const`는 전역 프로퍼티가 되지 않는다.
> `APP_VERSION` 같은 값은 같은 스코프에 프로브를 붙여 확인한다.

v11.14부터 다음 안전 회귀도 함께 검사한다.

- 이미지 자동 DB 일치가 사람 확인 전 종합 소견에서 제외되는지
- 의료기록 기재 약과 조사관 확인 약만 임상 정보에 사용되는지
- `blank_confirmed` / `unreadable` / `not_provided` 상태가 구분되는지
- 실제 재현 사례인 `DT20` ↔ `D120`의 `T`/`1` 혼동 후보가 유지되는지
- 그룹 전용 업로드 이벤트가 한 알 모드 버튼까지 잡지 않는지

- 연구기록·CSV에 API 키·토큰이 포함되지 않는지

### sample-dataset.js

`samples/`에 있는 **모든** 고정 샘플 팩을 검사한다. 팩은 각자 PC에서 만들어
커밋하므로 여기서 걸러 두지 않으면 깨진 팩이 배포까지 나간다.

- ZIP 크기·SHA-256이 매니페스트와 일치하는지
- 사진 수 = 건수 × 2, case_id 중복 없음, 001부터 번호 연속
- 매니페스트의 사진 해시가 ZIP 안 실제 JPEG과 맞는지(표본)
- 정답지가 앱 검증기를 통과하고 사진과 짝을 이루는지
- 무작위 5건 뽑기가 성립하고 한 바퀴 배치 수가 맞는지

### sample-dataset-builder.js / random-batch.js

고정 샘플 확장(120건)과 무작위 출제를 검사한다. 식약처 서버 없이 돈다.

- 세트 정의: 확장 세트가 기존 20건을 같은 순서로 포함하는지, 후보가 목표보다 많은지
- 후보 150건이 `pill_db.json`에 실제로 있고 이미지 URL 형식·모양·색상 다양성을 만족하는지
- 사진이 빠진 품목을 건너뛰고도 목표 건수를 채우며, case_id가 빈틈없이 이어지는지
- 목표를 채우면 남은 후보는 내려받지 않는지(불필요한 요청 방지)
- 만들어진 ZIP이 앱의 `validateDatasetRows`를 그대로 통과하는지
- 좌=앞면·우=뒷면 분할이 실제로 맞는지 (sharp 설치 시)
- 외부 `zip` 명령 없이 만든 ZIP이 두 번 만들어도 같은 바이트인지, JSZip으로도 풀리는지
- 무작위 출제: 같은 바퀴 중복 없음, 전량 순회, seed 재현, 5건 미만이면 뽑지 않음

### deidentify.js

개인정보 탐지 규칙과 의료기록 안전 게이트를 검사한다.

- 성명·주민등록번호·생년월일·전화번호·이메일·환자번호·주소가 텍스트에서 잡히는지
- OCR이 라벨과 값을 다른 토큰으로 쪼갠 경우, 간격·잡음이 섞인 경우까지 잡는지
- 약물 용법 같은 비개인정보를 개인정보로 오탐하지 않는지
- **의료인 성명**(담당의사·처방의사·주치의·집도의·판독의·조제약사)이 잡히는지 —
  이 규칙이 없던 동안 진단서·처방전 하단의 의사 이름이 그대로 남아 합성 문서 배치의
  항목 재현율 상한을 88.2%로 묶고 있었다
- 같은 규칙이 **서식 문구를 가리지 않는지** — "의사 표시", "의사 소견", "담당의사 서명",
  "검사자 확인"은 남아야 한다. `의사`·`약사`는 콜론이 붙었을 때만 라벨로 인정하고,
  값은 흔한 성씨로 시작하며 서식 용어가 아닐 때만 성명으로 본다
- 긴 직함이 짧은 직함보다 **먼저** 매칭되는지 — `판독의`가 앞서면 "판독의사 조은결"에서
  라벨이 토큰 중간에서 끊겨 이름 대신 직함이 가려진다
- 확인 전에는 비식별화 사본이 저장되지 않고, 가림을 고치면 확인이 취소되는지

### doc-log.js / doc-redaction.js / rule-ceiling.js / synthetic-profile.js / doc-samples.js

문서 비식별화 성능 수치를 만드는 세 갈래를 검사한다.

- 처리기록: 결과 분류(자동/부분수동/전부수동/실패), 조건별 합산, 실패 복구율
- **`/field` 실사용과 `/deid-report` 직접 테스트가 같은 분모에 섞이지 않는지** — 섞이면
  시험 삼아 열 번 돌린 것이 실사용 성능으로 둔갑한다. 출처 필드가 없던 옛 기록은 실사용으로 센다
- 요약 문장이 어느 통을 요약한 것인지 밝히는지, CSV에 `source` 열이 있는지
- 합성 세트 설명: 서식의 칸을 라벨 단위로 세는지(환자 이름과 의사 이름을 "성명"으로 합치지 않는지),
  값 가짓수가 적은 칸을 짚어 주는지, 촬영 조건을 음영 합성/기하 왜곡으로 갈라 분류하는지
- **주민등록번호가 실제로 발급될 수 없는 조합인지 값으로 확인하는지** — 되짚기 표 전체와
  커밋된 팩 양쪽을 검사한다. "합성값입니다"는 주장이고, 월·일을 세는 것이 근거다
- **기록에 개인정보·파일명·인식 글자가 섞이지 않는지**
- 성능 문장에 표본 수·조건·한계가 반드시 들어가는지
- 채점기: 항목 단위 재현율, 여러 상자로 나눠 덮은 경우 인정, 살짝 걸친 상자는 불인정
- **문서를 통째로 칠해 재현율 100%를 만드는 꼼수가 과잉 가림 배수로 드러나는지**
- 주 지표 교체: 고위험 항목(주민등록번호·개인식별번호) 재현율이 전체 평균에 묻히지 않는지,
  문서당 평균 누락 수와 누락 수 분포(0/1/2개 이상)가 나오는지
- **표본이 없을 때 0%가 아니라 "없음"으로 보고하는지** — 0%는 성능이 나쁘다는 뜻으로 읽힌다
- 규칙 상한선: 값의 일부만 걸친 탐지를 성공으로 세지 않는지, 라벨·값이 없는 옛 정답지에서
  상한 0%를 지어내지 않는지, 규칙 공백과 OCR 손실을 갈라 적는지
- **커밋된 정답지에 항목별 라벨·값이 실제로 들어 있는지**, 그리고 그 정답지의 규칙 상한이
  100%인지 — 떨어지면 어느 라벨이 규칙에서 빠졌는지를 실패 메시지가 알려준다
- 합성 문서: 정답지 크기가 실제 이미지와 일치하는지, 회전·축소 좌표 변환이 맞는지
- **정답 상자 안에 실제로 글자(어두운 픽셀)가 있는지** — 좌표가 밀리면 표본이 무의미해진다
- 합성 주민등록번호가 실제로 발급될 수 없는 조합인지
- **저장소에 커밋된 합성 문서 팩**의 정답 좌표가 실제 이미지·글자와 맞는지(조건마다 한 건씩)

### doc-batch.js

합성 문서 배치 측정과 `/deid-report` 화면을 검사한다.

- 한 문서가 터져도 배치가 계속되고 **실패 문서가 분모에서 빠지지 않는지**

- 측정 문장이 **"완전 비식별화"라는 이름을 쓰지 않는지** — 법적 안전으로 오해된다
- 규칙 상한선이 배치 결과에 실려 실측치와 나란히 문장에 나오는지,

- 직접 테스트가 **사본을 만들지 않는다는 사실을 화면에 적는지** — 없으면 여기서 눌러 본 것으로
  비식별화를 마쳤다고 오해한다
- 실사용 수치가 출처로 걸러지는지, 직접 테스트 기록에 출처가 붙는지

  설명은 그대로 남아 조용히 거짓말이 된다
- **측정 전에 결과 버튼이 보이지 않는지** — `display`를 지정한 컨테이너는 브라우저 기본
  `[hidden]{display:none}`을 덮어쓴다
- 측정 화면이 비식별화 사본을 만드는 경로를 부르지 않는지
- `/deid-report` 경로가 배포 설정·로컬 서버·스크립트 로드 순서에 모두 반영됐는지

### case-points.js

알약별 정확성을 판정(0/20/40)만이 아니라 0~40 점수로 직접 매기는 기능을 검사한다.

- 직접 적은 점수가 판정 배점보다 우선하는지, 0점도 유효한 입력으로 받는지
- 빈칸·공백·범위 밖·헛값이면 판정 배점으로 되돌아가는지(`Number(' ')`가 0이 되는 함정 포함)
- 점수칸이 없는 옛 기록이 예전과 똑같이 계산되는지
- 고친 점수가 총점·누적 정확도·CSV `accuracy_score`에 반영되고 판정은 `verdict` 열에 남는지
- 저장을 거쳐도 알약별 점수가 유지되는지
- 판정 셀렉터가 점수칸까지 함께 잡지 않는지

### run-store.js / metric-glossary.js

누적 연구결과의 저장과 그 숫자들의 설명을 검사한다.

- 저장 전 공급자 원본·산정 근거 문장을 덜어내되 총점·판정은 남기는지(원본 훼손 없이)
- 저장공간이 가득 찼을 때 **성공했다고 거짓 보고하지 않는지**, 몇 배치를 덜어냈는지 알리는지
- 시크릿 모드처럼 저장이 막힌 경우를 구분해 알리는지
- 백업 파일에 이미지·공급자 원본이 섞이지 않는지, 잘못된 파일을 거르는지
- 복원이 덮어쓰지 않고 합치며 같은 배치를 두 번 세지 않는지
- 남은 저장 여유를 용량과 보관 상한 중 먼저 걸리는 쪽으로 계산하는지
- 저장을 거친 기록으로 누적 요약과 CSV가 그대로 만들어지는지
- 화면에 나오는 모든 지표에 산출 근거·의미·해석 주의·출처가 있고, 출처 파일이 실재하는지
- 낮을수록 좋은 지표(CER·Brier)가 그 방향을 밝히는지, 문서와 화면 설명이 일치하는지

## 테스트가 실제로 작동하는지 확인하는 법 (중요)

통과만 확인하면 의미가 없다. 버그를 일부러 심어 검출되는지 봐야 한다.

```bash
# tdz — img 선언 앞에 즉시실행 참조 심기
sed "s/const APP_VERSION = 'v[0-9.]*';/&\n(function(){ const t = img.front; })();/" \
  index.html > /tmp/neg.html && node tdz.js /tmp/neg.html   # FAIL 나와야 정상

# dom — appVer 스팬 제거
sed 's|<span id="appVer"></span>|<span></span>|' \
  index.html > /tmp/neg2.html && node dom.js /tmp/neg2.html # FAIL 나와야 정상
```

두 번째 대조군은 실제 위험을 드러낸다. 헤더 버전은 단일 출처를 위해
`document.getElementById('appVer').textContent = APP_VERSION;` 로 채우는데,
그 스팬을 지우면 **앱이 즉사한다.** 헤더를 손볼 때마다 dom을 돌릴 이유.

## 이 테스트로 잡히지 않는 것

원리상 Node에서 확인 불가 — 실기기 확인 필요.

- CSS 렌더링 (`.name-pend` 미확정 배지 등)
- GPT 응답 품질 (개조식/서술형 출력 형식, 각인 판독 정확도)
- 이미지 전처리 효과 (대비 곡선이 각인을 더 읽게 하는지)
- `detail:'high'` 의 실제 판독 개선
- 식약처 낱알 사진 로딩, 실기기 카메라·갤러리

## 아직 없는 테스트

인수인계 문서에 있던 나머지. 필요할 때 추가.

> 있어야 함"이 새 정답이다. 옛 테스트가 있었다면 지금은 실패한다(의도된 변경).
